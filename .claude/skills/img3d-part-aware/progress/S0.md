## Deviations from DESIGN.md (with reasons)
1. **"Byte identity" of image jobs** is checked on the engine's output bytes (`model.glb`, `preview.png`) and on the
   job-folder entry set. `job.json` is checked for key identity at every level and for value identity of
   `settings`. Ids, timestamps and timings are new per run, so `job.json` can never be byte-identical across runs.
2. **Literal key pins.** `LEGACY_JOB_KEYS` (and the nested settings/progress/result/stats/reference key sets) come
   from the fixture, as DESIGN says. The `JobOut`, `JobResultOut` and `/system` key sets are pinned as literals in
   the test, so a future schema change fails there instead of being followed silently.
3. **Hash-file CLI** has three modes (`--check`, `--add`, `--update [PATH…]`) instead of one regenerate flag. A single
   "regenerate everything" flag would let S1, while adding `generation_worker.py`, re-pin and hide an unapproved
   drift.
4. **Extra contract edits.** Small pointers were added outside the required sections so §1-§10 stay consistent with
   §11: the §1 layout lines, the §7 id prefixes, the §7.3 note on `ReferenceImage.source` and a §9 bullet on the
   part-aware container and lifecycle order.
5. **Fixture metadata** has the TRELLIS shape with fake values, rather than the fake engine's metadata, so the file
   looks like a real pre-change `job.json` and S10 can read `metadata.preprocess`.
