# S8 Retention (2026-10-16)

## Built
`services/run_retention_service.py` contains `RunRetentionService(*, settings, layout, stores, workflow_store)`. Its
constructor matches the kwargs the S1 container already uses in `_build_retention`, so no container edit was needed.
The container now builds it through `RETENTION_PATH` and starts it as the `run-retention` task through
`run_forever(retention_interval_s)`.
- **ig_ / sg_ runs:** only terminal runs are deleted. Runs older than `{imagegen,segmentation}_retention_days` go
  first (0 turns the age limit off, like job retention). Then the oldest runs beyond `max_stored_*` go, counting
  terminal runs only. A run in `WorkflowStore.active_child_ids()` is skipped but still counts toward the limit. That
  set is re-read before every delete.
- **Workflows:** the service applies the same age and count limits to `WorkflowStore.list_terminal()` and deletes
  through `WorkflowStore.delete()`, which refuses active workflows. A refused delete is not counted.
- **pa_ runs:** never deleted here, because they go with their job (§7.2). `cleanup_runs("part_analysis")` raises
  `ValueError`.
- **Export cache:**
  - It purges `cache/part_exports/<pa>/` folders when `RunStore.get(pa)` is None, i.e. the analysis was deleted or
    its job was removed by job retention, which runs no hooks. Anything in the cache root that is not a `pa_` id is
    left alone.
  - Then an LRU pass evicts files down to `parts_export_cache_max_gb`, ordering by `max(st_atime, st_mtime)`. A cap
    of 0 keeps nothing between passes.
  - `*.tmp` files younger than 1 h are left alone because an export is still writing them. Older ones are removed.
  - It never creates the cache root and never removes the folder of an existing analysis, so it cannot race the
    S10 export writer's mkdir.
- **Orchestration:** each pass runs as one `asyncio.to_thread`. Each section (ig, sg, workflows, cache) is guarded,
  so one failure is logged and the other sections still run. `run_forever` survives a failed pass. The service
  returns a `RunRetentionReport` and logs a summary line, the same style as `RetentionService`.

## Tests
- `test_run_retention.py`: 14 passed (1.2 s). It covers:
  - age and count limits per store (failed and cancelled runs count as terminal; queued and running runs are never
    touched)
  - setting days to 0 turns off the age limit only
  - pa_ runs are excluded
  - runs used by active workflows are skipped until the workflow ends
  - protection is re-read during a pass
  - workflow age and count limits through `delete()`, and a refused delete is not counted
  - orphan export purge (pa_ deleted, job vanished, never indexed; entries that are not ours are kept)
  - LRU order uses the later of atime and mtime, with fresh and stale `.tmp` handling
  - cap 0, and a missing cache root
  - section isolation, and `run_forever` resilience
  - the real app container builds the service and starts the `run-retention` task
- Full suite: `pytest test\backend test\aux_models` gave **409 passed, 2 skipped** (92 s). That is the baseline of
  392, plus these 14, plus 3 from other in-flight slices. There were no failures. `test_import_boundaries.py` is
  green.

## Requests
- **S11 (`WorkflowStore`):** retention calls `list_terminal`, `delete` and `active_child_ids` from a worker thread,
  so the real store must be thread-safe, like `RunStore`. `active_child_ids()` is called once per deletion candidate,
  so keep it cheap (in memory).
- **S10 (`PartFiles`):**
  - Write cache temp files with a `.tmp` suffix (the `utils.files.atomic_write_bytes` pattern), so in-flight exports
    are never counted or evicted.
  - `os.utime` a cached export on every cache hit, so LRU stays correct where NTFS last-access updates are off.
  - If a cached file vanishes between the lookup and the response, rebuild it, because eviction is hourly.

## Open issues
- The `RunStore` index keeps entries of pa_ runs whose job was removed by job retention, which runs no hooks. They
  are hidden by `_visible` and dropped at the next restart. Pruning them needs the job id, which the public API of
  an invisible run does not expose. The leak is minor; S1 could add a `prune_vanished_jobs()` if wanted.
