# F1 API layer: progress report (2026-10-16)

Slice F1 (UI_DESIGN.md §11, wave A): the typed part-aware API layer. Status: **done** for every check that needs no
browser and no unmerged slice. Nothing calls these modules yet, so app behaviour is unchanged. The bundle contains
none of the new route literals; the only runtime change is five extra `case`s in `ws.ts`.

## Built
- `src/api/partAwareTypes.ts`: the frozen §2.1 wire types. All 66 exported types are **strictly identical** to the
  §2.1 code block. A type-level `Equal<Spec.X, Mine.X>` check over every export ran against the block extracted
  verbatim from UI_DESIGN.md, plus a negative control that does fail. The only value export is `GRAPH_ISSUE_CODES`.
  The module is import-free apart from erased `import type`s. Plain `node --experimental-strip-types` imports it
  without any loader (checked).
- `src/api/types.ts` (append-only block at the end): `ImageSourceOut` and the `ReferenceImage.source?` interface merge
  (DESIGN §6.7). `WsServerMessage` is untouched.
- `src/api/ws.ts`:

  - Frames are parsed as `WsServerMessage | PartAwareWsMessage`.
  - `dispatch` has five new `case`s that `emit(type, message.data)`. Unknown types still hit `default: break`.
  - The header doc is updated.
- `src/api/features.ts`:
  - `getFeatures(): Promise<FeaturesResult>`. A 404 resolves to `{kind:'legacy'}` (with or without an error
    envelope). A 401 throws and runs the expire hook.
  - `listModels(p?)` (returns `.items`), `getModel`, `loadModel`, `unloadModel`.
- `src/api/imageGenerations.ts`: `createImageGeneration`, `listImageGenerations(p?)`, `getImageGeneration`,
  `cancelImageGeneration`, `deleteImageGeneration`, `postCandidateUse(id, index, body)`.
- `src/api/segmentations.ts`: `createSegmentation`, `listSegmentations(p?)`, `getSegmentation`, `cancelSegmentation`,
  `deleteSegmentation`, and the typed-but-unused `getSegmentationLabels` and `getSegmentationSource`.
- `src/api/partAnalyses.ts`:
  - `createPartAnalysis(jobId, options?)`: no body when `options` is undefined.
  - `listPartAnalyses`.
  - `getLatestPartAnalysis`: a 404 with `details.reason === 'none'` returns `null`; every other error throws.
  - `getPartAnalysis`, `cancelPartAnalysis`, `deletePartAnalysis`.
  - `getPartManifest(manifestUrl)`: raw JSON from the payload URL, header auth through `absolutePathConfig`.
  - Typed but unused: `getPartAnalysisBuffer` (returns `{data, dtype, count}` from `X-Img3d-Dtype` /

- `src/api/workflows.ts`:
  - `getWorkflowCatalog(etag)`: sends `If-None-Match` and passes
    `validateStatus: (s) => (s >= 200 && s < 300) || s === 304`. A 304 returns `{kind:'not_modified'}`; otherwise
    it returns `{kind:'ok', data, etag}`.
  - `validateWorkflow(body, signal?)`, `createWorkflow`, `listWorkflows(p?)`, `getWorkflow`, `getWorkflowGraph`,

- `src/api/files.ts`:
  - `fileUrl` (token-aware `resolveApiUrl`).
  - `withQuery`.
  - `downloadFile(payloadUrl, {fallbackName, sizeHint, onProgress, signal})`: header auth, a Blob response, no

    decode).
- `test/frontend/unit/api_layer.test.mjs` (new; F1 owns the modules it tests): 65 assertions covering:
  - every route's method, path, params and body bytes (bodies are passed through byte-identical, key order kept);
  - the three status mappings;
  - the abort signal and Bearer header;
  - the file helpers, including a JSON error inside a Blob becoming an `ApiError`;
  - WS dispatch of the five types, with unknown and garbage frames ignored and `ping` answered with `pong`.

  The api modules are not pure, so the test registers an in-process loader hook. The hook resolves extensionless
  specifiers under `frontend/src` to `.ts` and replaces `import.meta.env` with `({})`. HTTP goes through a fake
  axios adapter; nothing touches the network.

## Deviations from UI_DESIGN.md (all additive; no §2.1 type changed)
1. **`ItemsOut<T>` added to `partAwareTypes.ts`.** This is the DESIGN §6 `{items}` list envelope, used by the five
   list functions instead of repeating a local wrapper in each module. It does not affect any §2.1 type.
2. **Type imports in `partAwareTypes.ts` use `'./types.ts'`** (§2.1 shows `'./types'`). They are erased either way.
   The explicit extension satisfies the "explicit `.ts`" rule for pure modules.
3. **Named helper types for §2.2's inline shapes:** `ListModelsParams`, `ListImageGenerationsParams`,
   `ListSegmentationsParams`, `ListWorkflowsParams`, `WorkflowCatalogResult`, `WorkflowGraphOut`,
   `DownloadFileOptions`, `PartBufferData`. They are structurally identical to the inline §2.2 signatures.
4. **Typed-but-unused routes** (§2.2 last paragraph) are concrete functions:
   - `getSegmentationLabels` / `getSegmentationSource` → Blob;
   - `getPartAnalysisBuffer` → ArrayBuffer plus dtype and count;
   - `getPartAnalysisLog` → text.

   All of them fetch as Blob so that a JSON error body still becomes a proper `ApiError` (the existing
   `parseBlobBody` path).
5. **`getWorkflowCatalog` ETag source:** it reads the `ETag` header and falls back to the body `etag` when the header
   is not readable. That happens cross-origin without `Access-Control-Expose-Headers`, e.g. with
   `VITE_API_BASE_URL`.
6. **`downloadFile` progress:** `onProgress` reports percent 0..100, like `downloadJobGlb`. It uses `event.total`
   when known, else `sizeHint`, else `null`.
